# Recommended local image architecture for PoseForge

## Decision

Add **ComfyUI local API** first. Offer **stable-diffusion.cpp** later as a lightweight CLI/Metal fallback. Keep **Diffusers** as an engineering reference/prototype layer, not a user-facing engine. Consider **InvokeAI** only as an alternative integration for deployments that value its full creative UI and Bearer/JWT multi-user API over ComfyUI's workflow ecosystem.

## Runtime comparison

| Runtime | Contract | Apple/CUDA | Queue and batch | Fit for PoseForge |
|---|---|---|---|---|
| ComfyUI | HTTP `/prompt` workflow JSON, upload/history/view, websocket progress; `comfy-cli` manages install/start | Apple Silicon, CUDA, AMD, Intel | Async queue; workflow batch nodes; one GPU normally executes one graph at a time | **Best primary local backend** |
| Diffusers | Python pipeline calls; no standard generation daemon/CLI | CUDA and MPS | Native batched tensors, but VRAM rises; MPS docs warn batches can be unreliable | Best custom prototype/test harness |
| InvokeAI | FastAPI/OpenAPI, session queue, Swagger, optional Bearer/JWT multi-user auth | Apple Silicon 16GB+ recommended; CUDA/ROCm | Managed queue/workflows | Strong standalone-app alternative |
| stable-diffusion.cpp | Excellent `sd-cli`; C API; RPC is device offload, not job API | Metal, CUDA, Vulkan, CPU and others | Spawned-process concurrency must be controlled by PoseForge | **Best true CLI**, secondary engine |

## Model options to present for approval

1. **FLUX.2 Klein 4B — Recommended default.** Apache-2.0, generation plus multi-reference editing, about 13GB VRAM in the official card, consumer-GPU target, commercially usable. Best balance of modern editing, speed, and licensing. Pose references should be passed as an explicit second reference, but it needs evaluation for strict pose adherence.
2. **Qwen Image Edit 2511 — Quality/multi-person tier.** Apache-2.0, official support for multiple input images, improved character and group consistency. Much heavier; budget 24GB CUDA or 32–48GB unified memory with quantization/offload as a validation target. Best candidate for couples/families and complex multi-reference edits.
3. **SDXL + Xinsir OpenPose ControlNet + ordinary IP-Adapter or PhotoMaker V1 — Exact-pose tier.** The most explicit skeletal control and viable on roughly 8–12GB CUDA/16GB+ Apple memory with offload. More moving parts and older image quality. Do not silently substitute FaceID/InstantID/PhotoMaker V2 because their InsightFace/checkpoint terms are research-only.
4. **FLUX.2 Klein 9B / FLUX dev/Kontext dev — Do not enable by default.** Their open weights use non-commercial terms unless separate rights are obtained. A 4B Apache model already covers the product need more cleanly.

## Hardware presets

- **4–8GB VRAM / 8–16GB RAM:** SD1.5 is the reliable floor; SDXL via offload/low-VRAM modes. Do not promise six-way parallel inference.
- **8–12GB VRAM / 16–32GB RAM:** SDXL exact-pose workflow; quantized/offloaded FLUX.2 Klein 4B may work, but full official target is about 13GB.
- **16GB+ VRAM / 32GB RAM:** FLUX.2 Klein 4B default and controlled batches.
- **24GB+ VRAM / 32–64GB RAM:** Qwen Image Edit 2511 or concurrent workers after benchmarking.
- **Apple Silicon:** 16GB is the practical SDXL floor; 32GB is preferred for FLUX.2 Klein; 48–64GB for Qwen-class experiments. On MPS, process collage poses sequentially because Diffusers documents unreliable batch inference under memory pressure. `stable-diffusion.cpp` Metal/GGUF is the most predictable lightweight Mac path.

These are deployment tiers, not guarantees; resolution, precision, quantization, and offload materially change memory.

## Six-output/concurrency behavior

- Keep PoseForge's six logical jobs and progress states.
- On one GPU, submit to one Comfy queue and let the runtime serialize graphs; for six variants of the same conditioning, use a workflow batch only when measured VRAM permits.
- For six different collage poses, use six queued jobs. “Parallel” at the UI/job level should not imply simultaneous kernels on one GPU.
- True parallel generation requires one worker per GPU (or carefully partitioned devices). Cap worker concurrency by detected device memory rather than always using six.

## Image input and HEIC

Do not send HEIC directly to any runtime. ComfyUI and Diffusers load through Pillow-style image inputs, while CLI runners support narrower codecs and none provides a stable cross-platform HEIC promise. Retain PoseForge's current ingestion boundary: auto-orient, convert ICC color to sRGB, strip unsafe metadata, normalize to PNG or high-quality JPEG, preserve the original separately if desired, and pass only normalized local paths/workflow uploads to engines. This also makes hashes, thumbnails, collage splitting, and retries deterministic.

## Adapter/API contract

PoseForge should expose one engine-neutral request:

```text
generate({
  identityImages[], poseImages[], prompt, negativePrompt,
  width, height, seed, outputCount, controls, jobId
}) -> { externalJobIds[] }
```

and capabilities such as `multiReference`, `exactPose`, `maxOutputs`, `supportsApple`, `licenseClass`, and `estimatedMemoryGb`. Store model ID, workflow version, seed, runtime version, elapsed time, and measured peak memory with each result.

For ComfyUI, PoseForge—not Comfy—should own the public token boundary. Bind Comfy to `127.0.0.1`, generate a per-install secret for PoseForge's own API if remote access is enabled, and never expose the stock Comfy or stable-diffusion.cpp RPC ports directly. InvokeAI is the only reviewed local runtime here with a built-in Bearer/JWT multi-user path.

## Adversarial review

- ComfyUI custom nodes can break across releases; pin the runtime, nodes, workflow JSON, and model hashes.
- A general multi-reference editor may preserve identity but miss exact limb geometry; acceptance requires a fixed local evaluation set, not showcase images.
- "Apache code" does not clear model weights or face encoders. The InsightFace dependency is the largest commercial-license trap.
- Batching six images may reduce throughput through swapping or out-of-memory retries; default to queued execution and unlock true batches only after a device benchmark.
